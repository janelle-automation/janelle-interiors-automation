The Grok connector

How a second media provider gets wired into a system that already has one — the circuit it runs on, the contract it has to honour, and the five moves that build it.

A connector here is not an integration screen or a third-party plugin. It is one file with four exported functions, sitting behind the same shape the Gemini renderer already uses: prompt in, reference images in, one piece of media out. Everything else in this document exists to keep that shape honest — the key, the cost, the clock, and the fact that a video cannot finish inside a request.

This is built. The five moves below are what was done, not what to do — the code is in the branch, it compiles, and it refuses in plain words until someone sets XAI_API_KEY and applies migration 0014.

01

What the connector is, and is not

The system already talks to two providers: Claude for reading and writing, Gemini for drawing boards. services/images.ts was written provider-shaped on purpose — its own comment says swapping providers should be a new function beneath that file's exports, not a change at every call site. Grok is the first test of that claim.

The connector owns

  • + One HTTP client. fetch with an AbortController, no SDK, so the timeout is ours.
  • + Provider vocabulary. request_id, generate_audio, respect_moderation — none of it leaks past the exports.
  • + Plain-sentence errors. A 401 becomes "the Grok key in Settings is not valid", never a 400 body on screen.
  • + Its own spend row. Every call lands on the usage report, successes and failures alike.

The connector never

  • – Holds a key. It asks aiSettings.ts, which decrypts the studio's key or falls back to the environment.
  • – Blocks on a video. It starts one and returns. The waiting happens somewhere no one is watching a spinner.
  • – Decides who may render. That is canWith(permissions, role, 'prompts', 'update'), checked before the tool ever calls in.
  • – Serves bytes to the browser. Storage and sealed grants already do that, for every file in the app.
02

The circuit

Two tracks through the same ten parts. An image completes inside one turn and comes back in the answer that asked for it. A video cannot: the provider hands back a request_id, the job is written down, and something polls until there is an mp4 to fetch. Press play, or step through it.

Five moves

In this order. Each one ends somewhere the work can stop safely, and nothing before move four is visible to anyone in the studio.

01

Prove the provider before you believe the docs

scripts/grok-probe.mjs · half a day

The video API is documented down to its status values. The image API is not: whether it takes n, response_format, aspect_ratio or a reference image under exactly those names is unconfirmed, and so is whether its returned URL expires. Settle it with one script against the real key, and write the answers into the plan — before anything in the app depends on them.

# one image, one video, every raw response printed
curl -X POST https://api.x.ai/v1/images/generations \
  -H "Authorization: Bearer $XAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"grok-imagine-image-2.0","prompt":"warm oak kitchen, morning light"}'

curl -X POST https://api.x.ai/v1/videos/generations \
  -H "Authorization: Bearer $XAI_API_KEY" \
  -d '{"model":"grok-imagine-video-1.5","prompt":"slow pan across the island","duration":6}'
# → { "request_id": "d97415a1-…" } then poll:
curl https://api.x.ai/v1/videos/$REQUEST_ID -H "Authorization: Bearer $XAI_API_KEY"
# → status: pending | done | failed | expired
02

Write the module, and nothing else

apps/api/src/services/grok.ts · new file

Four exports. They are the whole connector, and they are deliberately not Grok-shaped: a caller asks for an image or starts a video, and never learns what a request_id is.

export async function isGrokReady(orgId?): Promise<boolean>;
export async function generateImage(req, refs, ctx: CallContext): Promise<GeneratedImage>;
export async function startVideo(req: VideoRequest, ctx: CallContext): Promise<{ requestId; model }>;
export async function pollVideo(requestId, orgId?): Promise<
  | { status: 'pending' }
  | { status: 'done'; url; seconds; model }
  | { status: 'failed' | 'expired'; message }>;

/* Bounded inside what is left of the assistant's 40s turn — not the
   180s the board renderer asks for, which the 60s function outlives. */
const IMAGE_TIMEOUT_MS = Number(process.env.XAI_IMAGE_TIMEOUT_MS || 25_000);

Two rules the module holds on its own: cost is recorded by whichever call spends it — the image call books one image, and the poll that first sees done books seconds × rate — and every failure comes out as a sentence someone can act on, the way the Gemini path already turns a quota error into "enable billing on the project behind this key".

03

Give it a key it does not own

env.ts · lib/aiSettings.ts · routes/settings.ts

A third resolver beside resolveAi and resolveImageAi: same AES-256-GCM encryption, same 30-second cache, same rule that the key never reaches the browser — the settings screen gets the last four characters and nothing else. organizations.settings is readable by every member of the studio, which is exactly why the key is encrypted inside it.

xai_api_key_encrypted · xai_image_model · xai_video_model   // studio
XAI_API_KEY · XAI_IMAGE_MODEL · XAI_VIDEO_MODEL             // environment fallback

Worth knowing before you start: imageSettingsView and its save/clear siblings already exist in aiSettings.ts and are wired to no route and no screen. Image config is environment-only in practice today. Wire both while you are in there.

04

Hand it to Jenny — two tools, one of which lies if you let it

services/assistant.ts · TOOLS, runTool, TOOL_STATUS, TOOL_SOURCES

make_image follows the render_board handler almost line for line: check the permission, check the key, read the attachments as references, store the bytes, seal a grant, return a ref for the answer's items. make_video is the one that needs guarding.

return {
  job_id: job.id,
  status: 'rendering',
  estimated_cost_usd: videoCostUsd(model, seconds).toFixed(2),
  instruction: 'Tell them it is rendering and roughly how long. Do NOT put a file' +
               ' ref in the items — there is no video yet.',
};

Keep both descriptions tight. estimateTokens counts the tool block on every turn against a 5,000-token budget, and whatever the tools spend comes off the clamp on Jenny's output — so a verbose description is paid for by every answer she gives, forever.

05

Make the waiting real

migration 0014 · services/mediaJobs.ts · routes/ops.ts · AssistantAnswer.tsx

A media_jobs table, org-scoped by the same RLS policy the baseline stamps on every operational table. Then two pollers, because neither is enough alone: the browser while someone is watching, and a cron sweep every five minutes for everyone who closed the tab. Both call one finishJob(jobId), made safe against each other by a conditional update.

  start ──▶ pending ──▶ done      bytes in our storage, URL signed
              │  └────▶ failed    the provider's own sentence, passed on
              └───────▶ expired   gave up after ~10 minutes

Two details decide whether this works at all. The provider's mp4 URL is temporary — fetch it into the bucket the moment the job reports done, or last Tuesday's clip is a dead link. And an mp4 cannot come back through /api/assistant/file: the relay caps at 4.3 MB on Vercel, so video is delivered as a short-lived Supabase signed URL with a new preview: 'video', never as a download.

05

The voice half is already built

Worth saying plainly before anyone plans work for it. apps/web/src/lib/speech.ts already holds recognition, the studio's own vocabulary re-ranking (fed by GET /api/assistant/vocabulary, so "Casa Elar" survives being heard), echo suppression and speech output. Every hearing already reaches the server as spoken.alternatives. A spoken brief needs four things on top of that, all small:

Do

  • + Pass the alternatives through. A misheard material is a wasted dollar, and the model spots "oat flooring" better than the recogniser does.
  • + Confirm before spending. A misheard task is recoverable; a misheard $1.20 clip is not.

Don't

  • – Read the brief back aloud. The answer's speech field exists for exactly this: "Rendering it now, about a minute."
  • – Leave audio on. generate_audio defaults to true at the provider; a talking video plus Jenny speaking is two voices, and the echo filter will feed the soundtrack back as the next question.
